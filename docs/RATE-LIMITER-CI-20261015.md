# main 合并后限流间隔失败

PR #12 已合并为 `286ab90d7f59279fdd01675002cad4b3eacf6b41`，但其 [main CI 38760304410](https://github.com/znbsf/KazumiTV/actions/runs/38760304410/job/116509515342) 失败：`async_rate_limiter_test.dart` 的顺序调用间隔期望至少35ms，实测33ms。870项通过、1项失败，APK任务跳过。合并前PR成功不能替代这个main结果，未重跑掩盖失败。

## 判断与证据

旧实现使用DateTime.now预订未来时间槽，等待Future.delayed一次后直接放行。它没有用实际放行时间建立下一次期限，也没有复核唤醒时间。因此不是仅调整测试容差即可解决的可靠性问题。

日志没有记录DateTime/Stopwatch双时钟样本或定时器实际期限，不能断言该次33ms究竟由墙钟粒度、调度延迟、时钟变化还是多个因素造成。本地固定SDK的timer_patch.dart确实将duration取inMilliseconds；小数毫秒会截断，但这一点单独不足以解释7ms差额。Stopwatch用于经过时间，避免墙钟校准干扰。

先仅增加可注入经过时间/等待函数，保留旧时间槽算法，再运行两个确定性回归：

- 40ms期限的等待在33ms完成，旧算法立即放行，断言granted=false失败。
- 预约的40ms与80ms等待都延迟到100ms完成，旧算法给出 `[0,100,100]`，证明迟到会扎堆放行；期望 `[0,100]` 失败。

这两项都取得red日志，随后修复才转为green。它们证明算法对提前唤醒/迟到不健壮，不冒充当次Windows故障的完整系统级复现。

## 修复

默认以独立Stopwatch计时，仅串行化放行，不串行化调用方网络操作；按上次实际放行时间+period反复等待剩余时间，每次唤醒重新核对。正的小数毫秒向上取整，避免零延迟自旋。等待失败不污染后续队列。现有构造调用和run返回/异常语义保持。

真实调用点为Bangumi写操作250ms和收藏分页200ms。调度迟到时吞吐可能降低，这是保证最小间隔的预期代价，网络操作仍可并发。没有更改网络/认证/接口或外部规则。

首次调用测试原来断言宿主机器30ms内完成，改为可控时钟验证没有安排等待；它验证行为而非CPU速度。顺序/并发真实时钟测试原有35ms阈值没有放宽，run失败后仍保持限流测试保留。
