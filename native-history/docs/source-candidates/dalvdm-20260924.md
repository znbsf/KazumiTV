## 现场与改动

生产 APK `9EFBBEFC…` 上，实时验证码图由本轮截图识别并填写。提交后挑战消失，搜索页 HTTP 200、页面标题为“无职转生搜索结果”，但原规则的 `searchList=//div[@class='vod-detail style-detail cor4 search-list']` 匹配 0 个。页面实际包含 `main.search` 内的详情链接。第一版候选搜索返回 6 项，但原集表选择器为 0；从真实详情页更新集表为 `div.tab-pane.lists-box` 内的播放链接。候选文件仅调整名称、版本、搜索与集表 XPath，保留原站点地址、请求和验证配置。

测试 APK `77C4F0137061C3445C49840BC92F49129FA8C184AD3CAC004974393B4E9CCAFC` 的 `candidate-rule` 校验通过：生产解析器接受此 JSON、隔离仓库生效、未导入用户规则、9 项路径边界检查通过。真实候选搜索 6 项，目标第三季详情 3 线、每线 13 集。第 12 集逐线抽样：1 线 HLS 清单已解析，Media3 进入 HLS 片段读取时 `HttpDataSource.InvalidResponseCodeException: 403`，播放器报 2004；2 线 MP4 已解析并出现首帧，随后 15 秒内未推进到 5 秒，运行时出现 AudioFlinger 缓冲不足记录，但没有同期播放器错误；3 线媒体候选在播放前探测 HTTP 404。**0/3 线完成短播标准，候选尚不可发布。**

1 线的 403 发生在媒体片段请求，不能归咎于 XPath；当前播放器已经将解析请求的 headers 配为 Media3 HTTP 数据源默认请求头，但尚未证明站点所需鉴权是否充分。2 线首帧和解码器初始化说明视频已到达，后续是持续读取/缓冲或源端供应问题，现有日志不足以判成客户端解码错误。3 线是媒体端 404，未进入播放器。三者没有共同、可复现的客户端修复点，因此本轮不改生产播放器，不把 403/超时掩饰成候选规则通过。

网页、完整请求、媒体地址及截图仅在被忽略的 `artifacts/p1-source-snapshot/dalvdm-*` 与设备应用目录；版本化文档仅保留去敏后的现象。如站点媒体恢复或获准进一步验证鉴权，再按这三条线路分别复测；不能把搜索/集表修复等同于播放修复。固定 17 源统计仍记 `dalvdm` 未进入集表。
